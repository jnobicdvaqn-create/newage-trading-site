## 一、三层记忆机制概念解析

### 1.1 核心定义

三层记忆机制是一种结构化的信息分层管理策略，借鉴人类认知心理学中的工作记忆、短期记忆、长期记忆模型，将AI代理的信息存储分为三层：

| 层级 | 名称 | 特征 | 访问频率 | 信息类型 |
|------|------|------|----------|----------|
| **热层** | 工作记忆 | 每次加载 | 高频实时 | 当日待办、进行中任务 |
| **暖层** | 近期记忆 | 自动维护 | 中频周期 | 本周/本月进展、决策记录 |
| **冷层** | 长期记忆 | 按需查询 | 低频按需 | 经验教训、知识沉淀 |

### 1.2 技术架构（基于OpenClaw实现）

```
┌─────────────────────────────────────────────┐
│        三层记忆 × LanceDB Pro              │
├─────────────────────────────────────────────┤
│                                             │
│  🔴 热层（每次加载）                         │
│  ├── TODO.md（当日待办，≤50项）             │
│  ├── HEARTBEAT.md（当前关注点）             │
│  ├── AGENTS.md/SOUL.md（身份与规则）        │
│  └── autoRecall（LanceDB 向量注入 top-N）   │
│                                             │
│  🟡 暖层（自动维护）                         │
│  ├── memory/daily/（本周进展摘要）          │
│  ├── memory/YYYY-MM-DD.md（每日日志）       │
│  ├── Micro Sync → 验证+标注 scope           │
│  ├── Daily Wrapup → markdown 摘要           │
│  └── 去重：向量相似度 >0.85 跳过            │
│                                             │
│  🔵 冷层（按需查询）                         │
│  ├── memory/learning/（业务学习沉淀）       │
│  ├── MEMORY.md（长期记忆索引，≤8KB）        │
│  ├── archive/（从暖层退休的文件）           │
│  └── LanceDB 全量（向量搜索可达）           │
│                                             │
├─────────────────────────────────────────────┤
│  排程维护机制：                             │
│  ├── Micro Sync（每天5次，扫session决策）   │
│  ├── Daily Wrap Up（每天01:00，结构化摘要） │
│  └── Weekly Compound（每周03:00，减脂蒸馏） │
└─────────────────────────────────────────────┘
```

### 1.3 双引擎分工

| 引擎 | 职责 | 触发方式 |
|------|------|----------|
| **LanceDB Pro** | 实时抓取 + 向量存储 + 混合检索 + rerank | 自动（autoCapture/autoRecall） |
| **三层记忆** | 结构化分层 + 排程维护 + scope隔离 + 人类可读 | cron排程 + 手动管理 |

**简单说：LanceDB做实时引擎，三层记忆做管理策略。**

## 二、当前问题分析

### 2.1 任务遗漏的根本原因

基于执行纪律铁规的分析，任务遗漏存在五大症结：

| 症结 | 表现 | 根因 | 发生频率 |
|------|------|------|----------|
| **接收不确认** | 不复述任务就动手 | 没理解就执行 | 高频 |
| **执行不验证** | "应该成功了"就继续 | 盲目自信 | 极高频 |
| **验证不独立** | 只看执行输出不看结果 | 没有二次确认 | 高频 |
| **汇报无证据** | "已处理"无验证结果 | 不汇报具体证据 | 中频 |
| **归档不及时** | 任务完成后不记录 | 记忆丢失 | 高频 |

### 2.2 执行不闭环的症结

根据执行纪律铁规定义，闭环流程应为：

```
主人指示 → 理解确认 → 执行 → 验证 → 汇报 → 归档 → 主人确认完成
                                                      ↑
                                                 如果没有确认
                                                 ← 继续跟进直到确认
```

**当前缺失的环节：**

1. **理解确认缺失** - 不复述任务含义
2. **验证环节缺失** - 不用独立命令验证
3. **归档环节缺失** - 不更新TODO.md/memory
4. **跟进环节缺失** - 不等主人确认就结束

### 2.3 记忆机制如何解决

三层记忆机制通过**分层存储 + 自动排程 + 强制归档**解决上述问题：

| 问题 | 解决方案 | 记忆层 |
|------|----------|--------|
| 接收不确认 | 热层加载TODO.md，必须确认任务存在 | 热层 |
| 执行不验证 | Micro Sync每小时检查执行状态 | 暖层 |
| 验证不独立 | 强制验证步骤写入每日日志 | 暖层 |
| 汇报无证据 | Daily Wrapup自动提取验证结果 | 暖层 |
| 归档不及时 | Weekly Compound强制迁移到冷层 | 冷层 |
| 跟进缺失 | HEARTBEAT.md维护未完成任务 | 热层 |

## 四、可执行SOP

### 4.1 任务创建SOP

**触发条件：** 收到主人任务指示

**执行步骤：**

| 步骤 | 动作 | 验证方法 | 输出 |
|------|------|----------|------|
| 1 | 复述任务确认理解正确 | 主人回复确认 | 无 |
| 2 | 判断任务优先级（P0/P1/P2） | 对照紧急程度标准 | 优先级标签 |
| 3 | 分配责任人 | 确认责任人可用 | 责任人ID |
| 4 | 写入TODO.md | `grep`验证写入成功 | TODO更新记录 |
| 5 | 汇报写入成功 | 告知主人任务已登记 | 汇报消息 |

**示例：**

```bash
# 步骤4验证
grep "任务关键词" ~/openclaw/workspace/TODO.md
# 应返回任务行，否则失败
```

### 4.2 任务执行SOP

**触发条件：** TODO.md中有待执行任务

**执行步骤：**

| 步骤 | 动作 | 验证方法 | 输出 |
|------|------|----------|------|
| 1 | 执行任务第一步骤 | 执行命令输出日志 | 执行日志 |
| 2 | 用独立命令验证步骤结果 | `grep`/`curl`/`cat` | 验证结果 |
| 3 | 如果失败，记录原因并重试 | 检查错误日志 | 错误记录 |
| 4 | 重复直到所有步骤完成 | 全部验证通过 | 完成标志 |
| 5 | 写入YYYY-MM-DD.md执行记录 | `cat`验证写入 | 日志文件 |
| 6 | 更新TODO.md状态为进行中 | `grep`验证更新 | TODO更新 |

**禁止行为：**
- ❌ 不说"应该成功了"
- ❌ 不用执行命令的输出作为验证结果
- ❌ 不跳过验证步骤

### 4.3 任务完成SOP

**触发条件：** 任务所有步骤验证通过

**执行步骤：**

| 步骤 | 动作 | 验证方法 | 输出 |
|------|------|----------|------|
| 1 | 最终验证（汇总所有验证结果） | 独立命令再次检查 | 最终证据 |
| 2 | 更新TODO.md状态为已完成 | `grep`验证更新 | TODO更新 |
| 3 | 汇报完成（带验证证据） | 主人回复确认 | 汇报记录 |
| 4 | 写入YYYY-MM-DD.md完成记录 | `cat`验证写入 | 日志文件 |
| 5 | 如果有经验教训，写入learning/ | `ls`验证文件存在 | 学习文件 |

**汇报格式：**

```markdown
**任务完成汇报：**

**任务：** [任务名称]
**执行人：** [责任人]
**执行时间：** HH:MM - HH:MM

**验证步骤：**
1. [验证方法1] → 结果：[具体证据]
2. [验证方法2] → 结果：[具体证据]

**最终结果：** ✅ 完成

**归档位置：** memory/YYYY-MM-DD.md
```

### 4.5 防遗漏机制

#### 三级检查清单

| 级别 | 检查内容 | 频率 | 执行人 |
|------|----------|------|--------|
| **一级（实时）** | TODO.md任务状态 | 每次任务变更 | 任务执行人 |
| **二级（周期）** | 进行中任务是否卡住 | 每2小时 | 助理二号 |
| **三级（全局）** | 全域问题扫描 | 每周五 | 星期五三世 |

#### 僵尸任务定义

| 状态 | 定义 | 告警级别 |
|------|------|----------|
| 进行中>24h未更新 | 黄色告警 | 提醒责任人 |
| 进行中>48h未更新 | 橙色告警 | 飞书通知主人 |
| 进行中>72h未更新 | 红色告警 | 启动Plan B |

#### 验证铁律

**每次验证必须包含：**
1. 独立验证命令（不依赖执行输出）
2. 具体验证结果（不说"应该成功"）
3. 验证时间记录（写入日志）

**全域搜索标准流程：**

```bash

# 第二步：列出含旧内容的文件
find ~/openclaw/ ~/.openclaw/ -type f \( -name "*.py" -o -name "*.json" -o -name "*.md" -o -name ".env" \) ! -path "*/node_modules/*" ! -path "*/.git/*" -exec grep -l "旧内容" {} \;

# 第三步：统一替换
# [替换命令]

# 第四步：验证旧内容残留=0（必须执行）
grep -rn "旧内容" ~/openclaw/ ~/.openclaw/ 2>/dev/null | grep -v node_modules | grep -v ".git/"
# 应返回空，否则失败

# 第五步：验证新内容到位
```

## 七、总结与建议

### 7.1 核心价值

三层记忆机制的核心价值在于：

1. **结构化分层** - 不同重要度的信息存储在不同层级
2. **自动排程** - Micro Sync/Daily Wrapup/Weekly Compound自动维护
3. **强制归档** - 任务完成必须记录，防止记忆丢失
4. **验证闭环** - 每步必验证，结果带证据
